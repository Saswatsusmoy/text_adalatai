Assignment data starts as parallel PDFs (and legacy clean text). The pipeline turns them into filtered sentence pairs and a frozen document-level train/dev/test split. External legal bitext is a separate Stage A path (next pages) and is not required to finish this phase.

Inputs

SourceWhat it isRole in pipeline
data/hindi/original/*.pdf30 Hindi judgment PDFs (custom font encoding)OCR input for the Hindi working corpus
data/english/clean/*.txtNumbered body paragraphs only (no headers/parties)EN input; PDF text layer is unreliable for Hindi but fine for English
data/hindi/clean/*.txtLegacy Windows-extracted text; 5 docs corrupted (? glyphs)Not pipeline input; kept for audit / comparison

Asymmetry by design: EN is body-only (clean files), HI is full document OCR (headers + parties + body). The alignment filter keeps only 1-1 mutual-best correspondences, so Hindi header sentences become orphans and never reach training. The model never sees document structure -- it gets independent (en, hi) pairs, so the asymmetry does not leak into translation.

End-to-end flow

PDF EN/HI
  -> reextract_pdfs.py      # Tesseract OCR for Hindi (not PDF text layer)
  -> join_lines.py          # EN hard wraps + proper nouns
  -> join_hindi_lines.py    # HI OCR hard wraps (danda-aware, idempotent)
  -> segment_sentences.py   # spaCy EN; danda HI
  -> align_sentences.py     # LaBSE mutual-best + QC filters
  -> output_format.py       # doc-level 80/10/10, seed 42, frozen doc IDs
  -> data/processed/{train,dev,test}.jsonl

Two hard gates protect this chain (details in the steps below): make verify-ocr proves preprocessed/ is Tesseract OCR, and the join step is a verified fixed point, so make preprocess reproduces the committed data byte-for-byte.

Step details

1. Hindi re-extraction -- reextract_pdfs.py

Why: All 30 Hindi PDFs use custom font encoding. Ligatures are stored as positioned glyph components, so text-layer extractors return broken spacing, control chars, or (cid:N) placeholders. Doc 17 even transliterates.

How: Five backends were compared on Doc 6:

ToolTypeDoc6 timeDev charsIssue
pdftotexttext-layer0.028s4,657ligature spacing broken
PyMuPDFtext-layer0.012s4,657control chars
pdfminer.sixtext-layer0.088s4,657(cid:N)
pdfplumbertext-layer0.106s4,657same as pdfminer
Tesseract hinOCR~6s~6,027OCR noise, but real Devanagari

Decision: default backend Tesseract -l hin --psm 6 at 300 DPI (PyMuPDF render per page). Staging under data/hindi/preprocessed/ so originals are never overwritten.

The doc-6 regression (caught, fixed, guarded)

Five clean files (docs 6, 14, 22, 25, 26) were originally corrupted (0 Devanagari). Doc 6's working corpus later regressed to text-layer output -- byte-identical to the broken clean/6.txt (4,657 Dev chars, mid-word splits like भार ीय, सिसविवल) -- despite Tesseract being the documented method. A fresh re-OCR restored 6,027 Dev chars with correct ligatures; the old text-layer version is preserved under data/hindi/preprocessed/_backup_textlayer_20260802/. Docs 14/22/25/26 re-OCR was idempotent (they were never degraded).

OCR invariant is enforced, not assumed

Because a silent regression already happened once, reextract_pdfs.py now verifies its own output against Devanagari floors + text-layer marker words, run() flags degraded writes as failed, and make verify-ocr is a hard gate (exits 1 on issues). A negative test proves degraded text-layer input is caught. pdftotext is resolved from PATH, not a hardcoded Homebrew path. The tests that once wrote into the real data tree now use tmp_path, so running the suite can no longer clobber the fix.

2. English line join -- join_lines.py

Why: PDF extraction hard-wraps English mid-sentence (~44-74 chars/line).

How: Heuristic join when a line ends mid-phrase and the next starts lowercase or with a known proper noun. The proper-noun list is data-derived, not hand-picked: discover_proper_nouns.py scans all 30 docs for words starting continuation lines, keeps heads appearing >= 2 times, and cross-checks that each head is not a sentence starter. Result: 34 verified heads (Court, Appellant, Section, Allahabad, ...). The 50-word hand-curated list it replaced had 18 words that never occur mid-sentence (e.g. "C", "Union") and missed 12 real continuations (party names like Pandey, Rajbali).

Rules: never join across .!? or a numbered/bullet item; join when prev ends lowercase and next starts lowercase OR a known proper noun OR prev ends a digit (e.g. No.38).

Result: roughly 58% fewer non-empty EN lines after join (2,819 -> 1,176); the 13 long-line docs are untouched (zero false modifications).

3. Hindi line join -- join_hindi_lines.py

Why: Tesseract OCR hard-wraps Hindi mid-sentence at PDF line boundaries (median ~71 chars/line, verified over all 30 docs). A logical sentence spans 2+ OCR lines and only the last carries a danda (।). Because segmentation routes every danda-less line to the English spaCy path, wrapped fragments survived as truncated danda-less "sentences" and entered alignment: 806 / 1,458 (55.3%) of aligned HI texts lacked a danda -- the single largest root cause of alignment defects and downstream translation noise.

How: join_lines(text) buffers consecutive lines and should_join(prev, next) decides each boundary. Join unless any guard fires:

  • a blank line sits between the lines (paragraph boundary);
  • next starts a numbered item / bullet / list marker -- Arabic or Devanagari digits, short roman numerals, (क)/(॥), -/•;
  • prev ends in a sentence terminator (danda, tolerating trailing quotes/punct such as ।");
  • prev or next is a standalone header (<= 40 chars, danda-less, matching a header vocabulary/pattern: बनाम, निर्णय, उद्घोषणा, अस्वीकरण, न्यायमूर्ति..., X: -- data shows these are headers, not wraps). Checking next too stops a long wrap from absorbing a following header, which keeps the join idempotent.

Dates (DD.MM.YYYY, incl. Devanagari digits) also start with digits + dots, so they are exempt from the numbered-item guard: a date-start line is usually a mid-sentence continuation (54 real cases would otherwise be missed). The step writes preprocessed/ in place and is idempotent (re-running is a no-op).

Why the header rule is vocabulary-based, not just length: a plain "short line" cut would either over-join (absorbing निर्णय into a party line, which then cascades on the next pass -- the original non-idempotent bug) or under-join (splitting genuine short continuations like के साथ, प्रथम तल). A scan of all 30 docs showed 56/86 short next-lines are headers vs 31 real continuations, so the guard matches a header vocabulary/pattern and checks both prev and next. Verified fixed point: 0/30 docs change on a second join, and segment(join(preprocessed)) == segmented for 30/30 docs -- the committed data is reproducible from make preprocess.

4. Segmentation -- segment_sentences.py

Why: Alignment needs sentence units while preserving legal abbreviations.

How: English uses spaCy en_core_web_sm (a dependency parser that already handles Mr., No., v., U.P., Cr.P.C.), with Smt./Shri./Sri. protected via a period sentinel. Hindi splits on the danda । -- fast and correct for >95% of boundaries; language is auto-detected per paragraph by danda presence.

Why over-segment on purpose: danda-splitting produces short fragments (section headers, बनाम, numbered items). Rather than hand-merging, the design lets LaBSE alignment drop orphans and keep only strong 1-1 matches -- under-segmenting would merge two sentences into one unit and lose pairs irrecoverably.

Result (order of magnitude): EN ~2,495 sentences, HI ~3,221 after joining (was ~7,418 as fragmented OCR lines; danda-less fraction 60.7% -> 34.7%). Remaining danda-less HI lines are headers, citations, and colon intros -- legitimate standalone units.

5. Alignment -- align_sentences.py

Why: 29/30 docs have EN/HI sentence count mismatch; only document-level parallelism is guaranteed (EN ~2,495 sentences vs HI ~3,221 after joining -- a ~3:1 pre-join ratio that makes 1:1 line alignment impossible without embeddings).

How: LaBSE sentence embeddings, mutual-best pairing per document, then QC filters:

  • min similarity >= 0.5
  • EN:HI character ratio in [0.3, 3.0]
  • min length > 3 chars
  • EN Jaccard near-dedup 0.85 (drop weaker of near-duplicates)

Why mutual-best and not DP: the EN-HI similarity matrix is extremely sparse -- only ~0.1% of pairs score above 0.5 (Hindi over-segmentation + body-vs-full-doc content mismatch). DP forces an alignment for every EN sentence, manufacturing low-similarity pairs that all get filtered; mutual-best keeps only the strong 1-1 correspondences and lets the rest become orphans. Each HI sentence gets at most one EN partner by construction.

Why LaBSE over BGE-M3: BGE-M3 is more conservative and yields 111 fewer pairs (7.6% less) with cleaner low-band scores. On a 30-document corpus, losing that much recall is worse than the marginal quality gain -- LaBSE is retained as default (align_sentences.py accepts a one-line model swap).

Result: 1,422 pairs written to data/aligned/all.jsonl (1,458 before the Hindi join step; joined HI units are longer/complete, so mutual-best pairs shift slightly). Avg LaBSE similarity 0.78.

Alignment quality is imperfect -- thresholds are soft

The 0.5 similarity floor is deliberately loose to keep recall on a tiny corpus. On the current data the similarity distribution is: 0.5-0.6: 99 pairs (7%), 0.6-0.7: 183 (13%), 0.7-0.8: 412 (29%), 0.8-0.9: 656 (46%), 0.9+: 72 (5%). The 99 low-band pairs include genuine OCR-garbled dates and a few partial overlaps; a stricter floor (0.6) is a one-line change but was kept low after checking that it would drop ~100 borderline pairs. Known residual issues: OCR date corruption (12.06.1978 -> 42.06.4978), list-marker noise, and a handful of number-only / dangling-preposition fragments that pass the filters (3 number-only pairs, ~60 EN pairs ending in a bare preposition). These are documented, not silent.

6. Split -- output_format.py

Why: Sentence-level random splits leak the same judgment into train and test (the model would memorize judgment-specific phrasing, inflating dev/test scores). Splitting at the document level guarantees every doc is seen in only one split.

How: 30 document IDs shuffled with a fixed seed (42), then sliced 24/3/3. The resulting IDs are frozen as constants in src/config.py (TRAIN_DOC_IDS / DEV_DOC_IDS / TEST_DOC_IDS), and output_format.run() prefers these frozen IDs over re-shuffling -- so re-running the pipeline after a data fix never silently re-rolls the split:

train docs: 2,3,5,6,7,10-20,22,23,25-30  -> 1,110 pairs
dev docs:   8, 9, 24                     -> 128 pairs
test docs:  1, 4, 21                     -> 184 pairs

IDs live in src/config.py as frozen constants. Do not re-roll.

Partial re-align is merge-safe: align_sentences.run(merge=) refreshes only the requested docs and merges them into the existing all.jsonl (sorted by doc, then similarity), so a one-doc re-OCR does not wipe the other 29 docs' pairs. This is what made the doc-6 re-OCR fix low-risk: only doc 6's pairs were rebuilt, total stayed at 1,422.
