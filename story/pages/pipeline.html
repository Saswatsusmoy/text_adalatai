Assignment data starts as parallel PDFs (and legacy clean text). The pipeline turns them into filtered sentence pairs and a frozen document-level train/dev/test split. External legal bitext is a separate Stage A path (next pages) and is not required to finish this phase.

End-to-end flow

PDF EN/HI
  -> reextract_pdfs.py      # Tesseract OCR for Hindi (not PDF text layer)
  -> join_lines.py          # EN hard wraps + proper nouns
  -> join_hindi_lines.py    # HI OCR hard wraps (danda-aware)
  -> segment_sentences.py   # spaCy EN; danda HI
  -> align_sentences.py     # LaBSE mutual-best + QC filters
  -> output_format.py       # doc-level 80/10/10, seed 42
  -> data/processed/{train,dev,test}.jsonl

Step details

1. Hindi re-extraction -- reextract_pdfs.py

Why: All 30 Hindi PDFs use custom font encoding. Ligatures are stored as positioned glyph components, so text-layer extractors return broken spacing, control chars, or (cid:N) placeholders. Doc 17 even transliterates.

How: Five backends were compared on Doc 6:

ToolTypeDoc6 timeDev charsIssue
pdftotexttext-layer0.028s4,657ligature spacing broken
PyMuPDFtext-layer0.012s4,657control chars
pdfminer.sixtext-layer0.088s4,657(cid:N)
pdfplumbertext-layer0.106s4,657same as pdfminer
Tesseract hinOCR~6s~6,027OCR noise, but real Devanagari

Decision: default backend Tesseract -l hin --psm 6 at 300 DPI. Staging under data/hindi/preprocessed/ so originals are never overwritten.

OCR invariant is enforced, not assumed

A regression once put text-layer output back into preprocessed/6.txt (4,657 Dev chars vs 6,027 for OCR). Now reextract_pdfs.py verifies its own output against Devanagari floors + text-layer markers, run() flags degraded writes as failed, and make verify-ocr is a hard gate (exits 1 on issues). pdftotext is resolved from PATH, not a hardcoded Homebrew path.

2. English line join -- join_lines.py

Why: PDF extraction hard-wraps English mid-sentence (~44-74 chars/line).

How: Heuristic join when a line ends mid-phrase and the next starts lowercase or with a known proper noun. Proper nouns were mined from the corpus (34 high-frequency continuation heads: Court, Appellant, Section, ...).

Result: roughly 58% fewer non-empty EN lines after join.

3. Hindi line join -- join_hindi_lines.py

Why: Tesseract OCR hard-wraps Hindi mid-sentence at PDF line boundaries (median ~71 chars/line, verified over all 30 docs). A logical sentence spans 2+ OCR lines and only the last carries a danda (।). Because segmentation routes every danda-less line to the English spaCy path, wrapped fragments survived as truncated danda-less "sentences" and entered alignment: 806 / 1,458 (55.3%) of aligned HI texts lacked a danda -- the single largest root cause of alignment defects and downstream translation noise.

How: join_lines(text) buffers consecutive lines and should_join(prev, next) decides each boundary. Join unless any guard fires:

  • a blank line sits between the lines (paragraph boundary);
  • next starts a numbered item / bullet / list marker -- Arabic or Devanagari digits, short roman numerals, (क)/(॥), -/•;
  • prev ends in a sentence terminator (danda, tolerating trailing quotes/punct such as ।");
  • prev or next is a standalone header (<= 40 chars, danda-less, matching a header vocabulary/pattern: बनाम, निर्णय, उद्घोषणा, अस्वीकरण, न्यायमूर्ति..., X: -- data shows these are headers, not wraps). Checking next too stops a long wrap from absorbing a following header, which keeps the join idempotent.

Dates (DD.MM.YYYY, incl. Devanagari digits) also start with digits + dots, so they are exempt from the numbered-item guard: a date-start line is usually a mid-sentence continuation (54 real cases would otherwise be missed). The step writes preprocessed/ in place and is idempotent (re-running is a no-op).

The remaining 10.9% danda-less aligned texts are mostly standalone headers that happen to align, colon-terminated definition intros (... इस प्रकार है:-), and OCR-garbled citations. Known conservative limits: blank-line-separated wraps (e.g. doc 1 charge list) stay split, and headers longer than 40 chars merge into the adjacent line (harmless, as they are alignment orphans).

4. Segmentation -- segment_sentences.py

Why: Alignment needs sentence units while preserving legal abbreviations.

How: spaCy en_core_web_sm for English; danda-aware split for Hindi.

Result (order of magnitude): EN ~2,495 sentences, HI ~3,221 after joining (was ~7,418 as fragmented OCR lines).

5. Alignment -- align_sentences.py

Why: 29/30 docs have EN/HI sentence count mismatch; only document-level parallelism is guaranteed.

How: LaBSE sentence embeddings, mutual-best pairing, then QC:

  • min similarity >= 0.5
  • EN:HI character ratio in [0.3, 3.0]
  • min length > 3 chars
  • EN Jaccard near-dedup 0.85 (drop weaker of near-duplicates)

Result: 1,422 pairs written to data/aligned/all.jsonl (1,458 before the Hindi join step; joined HI units are longer/complete, so mutual-best pairs shift slightly). Avg LaBSE similarity 0.78.

6. Split -- output_format.py

Why: Sentence-level random splits leak the same judgment into train and test.

How: Document-level assignment, seed 42, roughly 80/10/10 by docs then by pairs:

train docs: 2,3,5,6,7,10-20,22,23,25-30  -> 1,110 pairs
dev docs:   8, 9, 24                     -> 128 pairs
test docs:  1, 4, 21                     -> 184 pairs

IDs live in src/config.py as frozen constants. Do not re-roll.
