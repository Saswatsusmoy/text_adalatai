4b. Selection harness -- anti-forget caps + z-scored primary (Phase 3 fix)

A deep-read of the training loop against the strategy doc found the code did not enforce what the docs promised. The docs specified a z-standardized multi-suite primary and hard anti-forget caps; the loop computed a raw weighted mean of chrF++ and picked argmax. That is exactly why the pure-B run's E_milpac drop (5.24 vs the 2.0 cap) was only caught by post-hoc analysis, never by the trainer.

What changed (harness code + tests + docs; no retrain):

GuaranteeBeforeAfter (Phase 3)
Checkpoint selection raw weighted mean, argmax z-scored weighted primary (Stage B) + hard caps; stage A unchanged unless opted in
Anti-forget caps only in YAML, never enforced stage_b_max_drop_<suite> enforced; capped-out eval never becomes best_primary and counts toward early-stop patience
NaN handling (DDP) rank 0 broke alone, rank 1 kept training → NCCL deadlock all ranks hit the collective (sync_nan_stop) before stopping
Resume of vocab-extended model missing new_embed_rows.pt silently reverted emb rows raises when required; grad mask reinstalled on resume
MPS fp16 training raw fp16, no scaling (numerics risk) fp32 master weights + mps autocast + GradScaler('mps')
MPS vs H200 batch parity implicit 16 vs 32, unverified explicit global_batch_size + warn/raise on mismatch
Frozen subsample integrity no check that pool matches the manifest file_sha256 prefix verified at launch (warn/raise)
Run provenance "A2 best" found by grep over run dirs {output_root}/runs.json registry: run_id → config, data, logs, best checkpoint

Exact selection formula (documented in src/training/selection.py, TRAINING_STRATEGY §5.3, DESIGN_DECISIONS §40):

z_i   = (s_i - mean_i) / std_i        if std_i > 0
z_i   = s_i - b_i                      else (single-row baseline: delta)
primary = sum_i(w_i * z_i) / sum_i(w_i)
# Stage B weights: I_dev 0.7, E_milpac 0.3; caps: I_dev 2.0, E_milpac 3.0
# mean/std = population stats over all gen_eval rows of the baseline run's eval log
# b_i = chrF++ at the baseline run's best-primary row

Why z-score + caps, not just weights: the suites live on different scales (I_dev ~49 chrF++, E_milpac ~56, E_anuvaad ~64). A raw weighted mean silently rewards whichever suite has the highest absolute score, so the intended 0.7/0.3 balance is not what the loop optimized. Z-scoring makes the weights mean what they say, and the hard caps are the anti-forget guardrail that a raw argmax ignores.

Cap rejection is verified, not theoretical

Independent check on realistic values: a checkpoint with I_dev rising (primary 5.4) but E_milpac dropping 5.46 is rejected (cap_ok: False) even though its primary is high. This is the exact pure-B failure mode the old loop would have shipped.

Ops notes (H200 + local)

  • torch.compile disabled under DDP (NCCL hang after first loss_eval).
  • bf16 + Flash/mem-efficient SDPA; fused AdamW when available.
  • Same data / LoRA surface / steps as local; dual GPU only changes wall clock.
  • MPS (local): fp32 master weights + mps autocast + GradScaler('mps'); verified on torch 2.13 that the scaler needs fp32 masters (it rejects fp16 gradients).
  • Selection logging: every gen eval row now records selection.mode, cap_ok, cap_violations, and per-suite z for archaeology.
  • Runs register into data/runs/runs.json at launch (config snapshot, data manifest, eval/train logs, best checkpoint path).
